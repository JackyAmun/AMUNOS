# AMUNOS — 未来路线报告

> 基于《AMUNOS_操作逻辑_生产工具_应用生态规划.md》(GPT 分析) 与当前代码库实测状态，给出面向未来的可行性报告。
> 原则：**保留 GPT 规划的"个人电脑创作精神"，但用本项目的真实约束校准优先级与实现路径。**

---

## 1. 现状盘点（实测，2026-08）

| 维度 | 当前状态 | 说明 |
|---|---|---|
| 内核大小 | **50924 B / 上限 53248 B** | 仅剩 ≈2.3KB 余量 → **新功能必须放用户态 ELF，勿进内核** |
| 图形 | VBE 640×480×16bpp + 软渲染器 | 渲染通路是 **80×25 字符格 + 汉字格**，**缺通用像素/画线/矩形 API**（PLOT/DRAW/游戏的前置） |
| 中文 | UTF-8 + GB2312 + HZK16(16×16 点阵) + U2GB 映射 + 替换框 | **已超额完成** GPT 规划第 4 优先级；下一步自然是**中文输入** |
| 用户程序 | 内核平坦加载 ELF，可访问内核 RAM | 能直写 softbuf 做 GUI（EDIT 已验证），但**无进程隔离**（架构特性，非缺陷） |
| 命令 | cd copy dir echo elf help install mov ren ser tcc time type ver zh cls lpt | 含 `CMDS.BIN` 命令→ELF 映射、`-?` 帮助、`/` 统一分隔符、大小写不敏感 |
| 生态 | BIN 只有 **TCC.ELF + EDIT.ELF** | 盘符 A/B/C(串口/并口/C: 字库)、CFD、DEVICE 已有底层 |
| 任务/GUI | 单前台任务 + 后台调度；EDIT 是真 GUI(鼠标/窗口) | 单窗口 GUI 已被证实可行；**多窗口尚需窗口管理** |

**一句话现状**：AMUNOS 已经拥有"能跑 C 程序"之外的一整层——中文、软渲染 GUI、真实鼠标、三盘 FAT、串口/并口。缺的不是"能不能画"，而是**把现有能力整理成稳定 API + 一批小而美的用户态工具**。

## 3. 核心技术缺口（必须先补，否则规划中的图形类应用全部卡死）

### 3.1 缺通用图形 API（syscall 层）
当前 fb_render 只服务"文本渲染"。PLOT、DRAW、PAINT、TETRIS、SHEET 表格线、MATH 函数曲线 **都需要原生画点/线/矩形/填充**。
- 建议新增 syscall：`FB_PIXEL`(画点 RGB565)、`FB_LINE`、`FB_RECT`、`FB_FILL`（可回退到矩形+填充）、`FB_TEXT_AT`(在任意 x,y 画字符/汉字)。
- 实现上 fb.c 已有 `fb_draw_cjk`/`fb_draw_glyph`/`fb_draw_box`，**画点内核只需 `vga_rgb565` 一个函数**，管线已通，工程量小但价值最大。

### 3.2 内核空间只剩 2.3KB → 坚决"用户态优先"
- **凡新增功能一律做成打进 A:/BIN 的 .ELF**，只在极必要时才加 syscall。
- 需要内核加号的情况：往 fb 画点/读点（若做成 syscall）、音频、新 API 常数。
- 若真需要更多内核空间，下一大步是**内核分页/按需换页**（大改，推迟）。

### 3.3 单前台任务的边界
一次一个交互程序就够支撑"工具逐个跑"的 DOS 式体验。**多窗口 GUI 是重构**，应放在最后（=GPT 规划中那批 Studio 软件的形态目标这一段），先用单窗口+全屏工具把生态做起来。

## 4. 分阶段路线图（结合 GPT 优先级 + 本项目成熟度，含预估）

### ▶ 阶段 A — 平台补齐 + 快速工具（1~2 周）
> 目标：把"已有能力"变成"稳定的工具体验"，顺带补上图形缺口。

1. **原生图形 syscall**：`FB_PIXEL / FB_XLINE / FB_FILL / FB_TEXT_AT`（前置，解锁一切图形应用）。
2. **第一批准用户态工具（BIN 派发，~1~2 天/个）**：
   - `SYSINFO.ELF` —— 数据全在：VER/CPU/MEM-AVAIL/DISK 类型/驱动状态/TASKS（复用现有内核全局）。
   - `CALC.ELF` —— 四则 + `()`，够用；`PLOT SIN(X)` 留到图形 API 后。
   - `VIEW.ELF` —— 分页查看文本（占位 24 行的精简 MORE）。
   - `HEX.ELF` / `SIZE.ELF` —— ELF 内容/段大小查看（TCC 调试刚需）。
3. **输入法初版**：拼音→GB2312，**反向用现有 U2GB 表**（map gb→py 或编码表）；候选条走现有弹窗模式（EDIT 已验证）。至此中文"显示+输入"闭环。

### ▶ 阶段 B — 开发闭环 + 首个创作工具（约 2~4 周）
> 目标：从"能做工具"到"在机内自举一套开发/创作"。

1. `BUILD.ELF`：包装 TCC（COMPILE→LINK→VERIFY→`/RUN`），实现规划 §8 的自举循环。
2. `AMUN WRITE`（从 EDIT 扩展）：+ 文档型排版、搜索/替换、`.AWD` 标记解析（正文/标题/列表）、`VIEW` 复用其渲染。
3. `SYNTH.ELF`（音乐起步）：先走 **PC 喇叭定时器**出节拍；AudioI/O 规划里做 SoundBlaster/AC97（新驱动，依赖硬件探测）。

### ▶ 阶段 C — 生态扩展（按兴趣排）
- **游戏**：PONG、SNAKE（图形 API 就绪后极低成本，验证 API + 鼠标/键盘）。
- **SHEET**：网格 + `SUM/AVG/MAX/MIN` + `.ASH`，表格线直接吃 FB_LINE。
- **DRAW / PAINT**：矩形/椭圆/填充/文本 + 鼠标，吃图形 API + 鼠标读取。
- **MATH/PLOT**：吃图形 API 画函数曲线。

### ▶ 阶段 D — 架构级（长远，非短期）
- **BASIC** 解释器（可走 TCC 编译成 MOV 而非逐行——成本更低）。
- **多窗口 GUI / 窗口管理**（重排上：先单窗口）。
- **网络**（串口已有，可先 XMODEM/点对点；RTL8139 驱动是独立大块）。
- **FAT 长文件名 + 中文文件名**（盘上有 UTF-8 中文名后自然出现，DIr 层现为 8.3）。
- **检索/全局搜索**（小文件系统里可用 CMDS/索引换速）。

## 5. 对 GPT 规划的保留意见（避免踩坑）

1. **"第一优先级 SYSINFO/CALC/VIEW/HEX" 认同**，但这些应是**用户态 ELF 而非内核**——GPT 规划容易让人误以为要往内核堆，本项目内核已接近满载。
2. **图形 API 应前置到第一优先级**。GPT 把"Framebuffer"放第四优先级，但它其实是 DRAW/PLOT/PAINT/游戏的地基——**对 AMUNOS 它是先决条件而非加分项**，应提到阶段 A。
3. **中文支持已领先规划**：规划 §21 还在说"第一段只需 ASCII+GB2312 常用"，本项目已做到 UTF-8 自动识别 + 全 GB2312 字库 + 映射反查。**输入法是下一步顺理成章**，无需再等。
4. **BASIC 建议别做逐行解释器**：TCC 已能编 C，若想要"更易上手"，做一个"BASIC 源码→调 TCC 编译的薄封装"性价比远高于自写解释器。
5. **不要为"统一大写输出/非常规命令"而在命令名上大改**：你现在 `DIR` 类语义已被用户习惯，`LIST` 只是审美差异；保持兼容优先，审美可后续。

## 6. 结论

AMUNOS 站在一个很好的分叉点：**中文 + 软渲染 GUI + 真鼠标 + TCC 自举**已经集齐，超过绝大多数自制 OS 演示项目。

未来最能放大现状价值的顺序：
1. **补原生图形 syscall**（解锁一切图形类应用）—— 最高杠杆。
2. **用一批 1~2 天的用户态小工具**（SYSINFO/CALC/VIEW/HEX）+ **输入法**，把"能跑"升级成"好用、有创作空间"。
3. **BUILD 自举 + EDIT→WRITE + SYNTH**，形成"在 AMUNOS 内做 AMUNOS 软件"的完整闭环。
4. 最后才考虑多窗口 GUI / 网络 / 长文件名等架构级重排。

> 一句话：**先把平台短板（图形 API）补上，然后用小而美的用户态工具把现有能力铺成生态；多窗口、网络这类大改放到生态成熟之后。**
